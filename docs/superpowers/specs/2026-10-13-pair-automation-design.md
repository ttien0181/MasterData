# Stage 4: controlled pair automation

The user confirmed controlled automation, precision target 99.5%, shadow evaluation, traceability and a stop mechanism. Continue the same inline implementation and final independent review as stages 1–3. Preserve uncommitted work; use the existing Compose only. No production activation is authorized by synthetic benchmark results.

## Design

Add queued AUTOMATION_SHADOW and AUTOMATION_APPLY operations using existing ownership, role, run lock, revisions, artifacts, worker leases and idempotency. Shadow reads a current v4 assessment and never changes decisions. Plan only strict MERGEABLE/A pairs with original rule MERGEABLE, no recovery/conflicts/shared evidence, still UNDECIDED. Build proposals through the genuine cluster guards with all negative/rejected edges; require complete direct eligible evidence for every member pair. Qualify certified cohorts before applying the component cap, so an uncertified prefix never hides a later qualified cohort. Component cohorts bind field signatures, subgroups, source systems and component record count. Preserve legacy auto_only behavior; automatic permission is granted exclusively by the new guarded route.

A server-configured, SHA256-pinned certificate binds server-owned user ID/configured data scope, production scope, source systems, current code and engine profile, independent/representative validation metadata, expiration and per-component-cohort observed counts. Recompute conservative Wilson 95% lower bounds, adjusted for multiple certified cohorts; all must meet 99.5%, have complete labels and no constraint violations. Counts are operator-attested validation evidence, not proof of independence generated by software. HTTP clients cannot supply a certificate or lower the target. Missing/malformed/expired/unpinned/synthetic certificates fail closed. Default automation is disabled. Existing synthetic reports cannot certify deployment.

Apply requires a sealed current shadow preview and its token. Revalidate snapshot, certificate, code, cohorts, current decisions, negative edges, complete components and cumulative per-run canary budget at publication under the run lock. Apply a bounded batch atomically; never accept a partial component. Keep ACCEPTED as the existing overlay contract, but store separate automatic provenance (certificate, cohort, operation and component), audit it as automatic, and expose it in UI. Manual amendment clears active automatic provenance while immutable operation/audit history remains. Final publication still runs the existing guards and remains explicit; applying automation does not finalize/export.

AUTOMATION_STOP permanently stops further automatic application in that run, including queued work, without undoing saved results. Stop is revisioned/idempotent and allowed while an automation worker computes; it immediately cancels its operation/task and retires a running owner under the shared lock. That worker must fail its publication fence and manual review resumes without waiting for a worker. A publication which committed before acquiring the stop lock remains saved. Normal manual review/amendment remains available. Cumulative budget is not refunded by amendment/retry/certificate replacement. Default cap: 20 components/run, configurable at server with a bounded maximum; max 20 members and 190 direct pairs/component.

UI presents a small controlled-automation panel with shadow count, qualified/capped count, blocked reason, explicit batch apply confirmation, and stop. Hide certificate internals; no probability score claims. Preserve outstanding client review intentions and disable automation while those require attention. Automatically accepted pairs are visibly labelled.

## Verification

RED/GREEN pure tests: confidence/sample/coverage/metadata/code/profile/source/expiry/pinning gates; manual-only recovery/D/shared/deferrals/veto/missing bridges; component canary bounds/cohorts. Real API/worker tests: read-only shadow, denied default application, positive isolated certificate fixture, sealed/tampered/stale/cross-run preview, code/certificate/config changes, stop and retry fences, preserved manual history, cumulative budget and publication. Migration 0031 adds nullable automatic provenance and advances HEAD; real Alembic tests preserve existing rows. Frontend tests cover disabled/stale/confirmation/stop/provenance. Docker/browser test default shadow/denial/stop; positive activation is tested only with isolated certificate fixtures, never described as production validation. Compare stage-3 benchmark shadow outcomes and certificate rejection; do not rerun unchanged matching unnecessarily.

## Alternatives and rulings

Relaxing the score or bypassing REVIEW would not establish the requested precision. A new learned model lacks independent production labels. Choose a certificate-bound, bounded workflow route because it provides concrete automation while keeping unvalidated cohorts manual. The certificate is an administrator-controlled operational attestation; correct labels, representative sampling and independent holdout remain external responsibilities. Pending stage-3 limitations (TC3 recall and TC4/TC13 workload) remain visible.
